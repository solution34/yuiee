# Yuiee 双人长期学习与工程实践路线

- 日期：2026-10-15
- 状态：用户确认采用；按月复盘调整
- 适用对象：两名新人，以 Yuiee 为长期实践项目
- 建议周期：约 12 个月；每人每周约 8～10 小时
- 低投入方案：每人每周约 5 小时，可延长至 12～18 个月
- 关联：[需求基线](./requirements-v0.2.md)、[架构评审稿](./architecture-v0.1.md)、[开发与验证计划](./delivery-plan-v0.1.md)

## 1. 路线目标与边界

目标不是尽快堆完功能，而是两人都完整经历：

需求分析 → 设计 → 任务拆分 → 实现 → 测试 → 评审 → 构建发布 → 真实使用 → 维护复盘。

执行原则：

1. 先交付很小但完整的版本，再增加业务深度和系统能力。
2. 需要什么就学习什么，每个知识点尽量对应一个可验证的小任务。
3. 用可运行成果、验收记录和独立解释能力判断进度，不以看课时长判断进度。
4. 时间不足就缩小任务或延后，不删掉测试、评审和验收。
5. 本路线不降低最终需求。v0.1、v0.2、v0.3 是学习增量，不是最终第一版；发布说明须列出缺失功能。
6. 不因计划获确认就视为架构已获批准，也不在未验证前宣布技术方案可行。

## 2. 起点记录

本次检查显示：

- 已有需求、架构和开发计划文档。
- `yuiee-template` 为 Electron + TypeScript + Vite + Forge 初始化模板，尚无业务闭环。
- 已有 oxlint、oxfmt 和类型检查脚本；尚无测试脚本，TypeScript 尚未开启完整 `strict`。
- React、SQLite、AI 适配器及 CI 尚未在所读工程中落地。
- `yuiee-implementation` 在父仓库记录为子模块指针，本地目录为空，未发现 `.gitmodules`，需核实来源和用途。
- 本次只进行文件与 Git 检查，没有安装依赖、运行应用或验证安装包。

先检查仓库结构，不直接删除子模块记录、建立嵌套仓库或搬动入口文件。确认代码来源后，通过独立 PR 决定正式应用目录。

## 3. 阶段一：基础与协作（第 1～6 周）

### 学习内容

- TypeScript：函数、对象、数组、模块、异步与类型。
- HTML/CSS：布局、表单、输入和反馈状态。
- React：组件、状态、事件、表单和副作用。
- Node/npm：依赖、脚本、锁文件和环境差异。
- Electron：主进程、preload、渲染进程的基本职责。
- Git：分支、暂存、提交、推送、PR、合并和简单冲突。
- 调试：报错、断点、调用栈和最小复现。

### 实践与产物

先在学习分支完成内存事项列表：输入、展示、修改、删除，不接 AI 或数据库。每人至少独立提交一个小功能 PR，评审对方一次，并在练习分支处理一次人为制造的文本冲突。

保留安装运行说明、PR 和简短学习记录。临时学习代码不自动成为正式业务设计。

### 退出条件

两人都能不依赖另一人现场操作，完成运行项目、小改动、验证、PR 和评审，并解释修改涉及的代码。

## 4. 阶段二：需求与设计（第 7～10 周）

### 实践任务

1. 用自己的话复述目标用户、场景、痛点和成功标准。
2. 从现有需求中整理 3～5 条核心用户故事。
3. 画低保真原型，讨论空状态、处理中、失败和成功状态。
4. 确认最小版本：手动输入标题与截止时间、本地保存、列表查看、编辑、删除、重启保留。
5. 列出暂不做的功能：AI、模拟排程、周日历、提醒、悬浮窗和自启动。
6. 评审现有架构，画出页面结构、保存数据流、数据表和失败路径。

产物是一页产品目标、用户故事、原型、验收清单和架构评审记录。最小版本中的手动录入是明确的用户保存操作，不允许自动或隐式写入。

### 退出条件

双方能一致解释做什么、不做什么、怎样验收；未确定问题有记录，不靠开发时临时猜测。

## 5. 阶段三：最小版本完整交付（第 3～4 个月）

阶段二完成后再推进本阶段，不因周数与月份重叠而强行并行。

### 实践任务

- 确定唯一正式应用目录；整理仓库问题，但保留需核实的历史和代码。
- 统一 Node/npm 版本，沿用 npm 和锁文件。
- 接入 React、严格类型检查、测试工具和现有静态检查。
- 先验证 SQLite：开发版和安装版均能写入、退出、重启读取。
- 实现手动事项的新增、查询、编辑、删除。
- 加入数据库迁移、输入校验、错误反馈和基础测试。
- 在 Windows CI 上执行安装、检查、测试和应用打包。
- 编写 README，在另一人的电脑上按文档安装使用。
- 为经过验证的提交发布 `v0.1.0` 学习版本，注明未覆盖最终需求。

任务尽量拆成一两次学习时间可完成的大小。工具逐步引入，每个配置都应知道用途。

### 退出条件

全新克隆可按 README 运行；Windows 安装版可以持久化数据；至少有核心校验单元测试和数据库集成测试；用户不依赖现场指导即可安装使用。

## 6. 阶段四：业务可靠性（第 5～6 个月）

使用人工构造的候选事项，不依赖真实 AI，先打通：

候选事项 → 模拟安排 → 用户确认 → 事务保存 → 日历展示。

### 学习与实践

- 分离界面、领域逻辑和数据访问。
- 草稿与正式事项隔离，画状态图并实现版本校验。
- 实现本地排程、时间范围校验、冲突检测和逐项问题反馈。
- 确认接口具备事务与幂等性；逐步补齐周/日视图。
- 以可控制的时钟测试时间边界，不依靠真实等待。

### 必须保留的验证证据

- 模拟不写入正式日程。
- 修改方案后旧版本不能确认。
- 双击及重试不创建重复事项。
- 缺少具体时刻必须澄清，无空位不强行安排。
- 预览后日程变化会在确认时再次校验。
- 事务中途失败不留下部分事项或孤立提醒。

### 退出条件

发布 `v0.2` 学习版本；正常流程可用，错误操作不破坏数据；双方能够解释事务、状态机、版本和幂等分别解决了什么问题。

## 7. 阶段五：AI 与外部系统（第 7～8 个月）

顺序：纯文字提取 → 结构化校验 → 图片粘贴预览 → 图片识别 → 流式展示 → 多轮澄清修改。

### 学习与实践

- 适配器、假服务、超时、取消、错误分类和有限重试。
- 流式事件的请求关联、订阅清理和中断恢复。
- 外部数据运行时校验；AI 输出不等于合法业务指令。
- API Key 安全存储、隐私告知、脱敏日志和费用控制。
- 自动测试不用真实 Key 和网络；真实 API 验证须明确授权并控制数据和费用。

### 退出条件

发布 `v0.3` 学习版本；可完成截图到日历的路径；断网、无效 Key、错误结构和断流都有反馈，不影响正式日历；他人事项不会自动加入，含糊时间必须澄清。

## 8. 阶段六：长期运行能力（第 9～10 个月）

### 实践任务

- 系统通知、托盘、自启动、悬浮窗和设置管理。
- 提醒去重、修改取消、启动恢复和错过提醒展示。
- 脱敏日志、版本信息、数据库升级、备份和恢复说明。
- 对安装版验证关闭主窗口、明确退出、Windows 登录、休眠唤醒、事项修改删除及升级。

应用明确退出后，不能依靠自身即时触发提醒；电脑关机也不能发送通知。按照架构处理错过提醒，并在文档中说明限制。通知触发与状态写入存在崩溃边界，需明确验证和记录，不能仅因使用事务就声称绝对不会重复或遗漏。

### 退出条件

候选发布版本在真实 Windows 会话通过验收；能解释启动、运行、关闭、退出、重启和升级行为。开发模式验证不能替代安装版验收。

## 9. 阶段七：试用、正式发布与维护（第 11～12 个月）

邀请少量知情同意的试用者；优先使用人工构造或获授权的数据，不随意收集聊天截图。

维护流程：反馈 → 复现 → 严重度判断 → 回归用例 → 修复 → 验证 → 修复版本。

区分故障、使用疑问和新需求；验证旧数据升级，记录已知限制。只做有明确收益的重构，不在发布前大规模改写代码。

### 最终交付与退出条件

- 源码、版本历史、需求与设计说明。
- 自动化测试、CI、Windows 安装包。
- 安装使用说明、数据位置、备份恢复及删除方法。
- FR-01 至 FR-15 的实现与验收证据。
- 发布记录、已知问题、后续计划和项目复盘。
- 阻断发布及严重缺陷关闭；已发布软件出现问题后可以持续修复，而非只能重写。

## 10. 双人轮岗与日常节奏

| 阶段 | A 主导 | B 主导 |
|---|---|---|
| 最小交付 | 页面和交互 | 数据保存与构建 |
| 业务可靠性 | 排程与确认服务 | 模拟方案和日历界面 |
| AI 接入 | AI 适配器 | 图片、对话与状态展示 |
| 长期运行 | 提醒与恢复服务 | 设置、托盘与窗口 |
| 正式发布 | 构建和发布记录 | 验收、文档与问题跟踪 |

主导不等于独占：另一人必须评审、运行并能解释关键实现。正式分工按双方时间和基础调整，但至少每阶段轮换一次主要职责。

- 每周：30～60 分钟同步，确认成果、疑点、风险和下一件事。
- 每两周：演示可运行结果，不只展示代码量。
- 每月：复盘范围、时间、质量和学习盲点，更新任务安排。
- 每阶段：对照出口验收，未通过就延长或缩小范围，不跳过。

每人每周约 8～10 小时可参考：学习 2 小时，编码调试 4～5 小时，测试评审文档 1～2 小时，同步复盘 1 小时。忙碌时降低并行任务数，避免一人积压多个未完成任务。

## 11. 任务与学习记录

每个任务至少记录：编号、目标、范围、负责人、评审人、验收步骤、测试证据和未解决问题。早期练习可用 `LEARN-001` 等编号，业务任务关联 FR 编号。

学习记录建议保持简短：

```text
本次解决的问题：
实际结果与验证方式：
遇到的错误及原因：
现在能独立解释的内容：
仍不理解的内容：
下一步：
```

可以用 AI 解释、拆任务和辅助编程，但合并前负责人必须能解释调用位置、输入输出、失败路径、模块归属、验证方法和排错入口。不理解时缩小改动并补学习，不继续堆生成代码。

## 12. 第一周任务清单

第一周只建立起点，不要求完成 React、SQLite、测试和 CI 全套建设。

- [ ] 双方确认每周可投入时间，约定固定同步时段。
- [ ] 分别检查 Git、Node、npm 环境并记录版本，不盲目升级。
- [ ] 核实 `yuiee-implementation` 的原始仓库和用途，记录处理建议，不直接删除。
- [ ] 阅读模板的 `package.json`、`main.ts`、`preload.ts`、`renderer.ts`，画出启动流程。
- [ ] 在模板目录尝试 `npm ci` 和 `npm start`，记录真实结果；失败则保留错误并排查，不标记通过。
- [ ] A 提交一个小型文案或样式 PR，B 评审并验证。
- [ ] B 提交运行说明或另一个小型修改 PR，A 评审并验证。
- [ ] 周末演示：双方各自运行项目，解释一次改动，确认第二周的一个学习重点。

第一周完成标准：两人都能运行或明确定位当前运行阻塞，并至少完成一次有验证记录的 PR 协作；后续再逐步实现阶段一的完整出口。
